# 长期记忆 G1：预计算的 bigram 索引（提案）

日期：2026-11-11。状态：**已实施（未提交）**，与提案的差异见第 8 节，验收结果见 [G1 7.8](MEMORY_G1_STORAGE.md)。上级文档：[G1 存储改造](MEMORY_G1_STORAGE.md)；依赖：[增量提交](MEMORY_G1_INCREMENTAL.md)。

## 1. 背景

在 pgstore 上实测（G1 7.7），5k 条记录时完整召回的 p95 为 54～67ms，阈值是 30ms。其中召回计算本身（state 已读好）占 34～43ms，与存储无关。CPU 剖析结果：

| 部分 | 耗时（5k，真实中文） | 占比 |
|---|---|---|
| `recall` 的文本打分 | 29.2ms | 约 85% |
| 其中 `bigrams`：每次查询为每条记录重新构造字符对集合，大量分配 `string` 与 `map` | — | CPU 的 51% |
| `Related`（图谱子图与 Personalized PageRank） | 5.3ms | 约 15% |

**目标**：

- 召回结果与现在**逐项相同**：相同的记录、相同的分数（浮点数逐位相同）、相同的顺序。
- 5k 条记录时召回计算的 p95 ≤ 8ms，完整召回的 p95 ≤ 30ms（含两次读取）。
- 以上都是估计，以第 7 节的测量为准。

## 2. 现有语义（必须保持）

`memory.go` 中的 `recall`：

1. 只考虑有效记录（`InvalidAt` 为零），并按 `Query.Kinds` 过滤。
2. 文档文本为 `r.Content + " " + strings.Join(r.Keywords, " ")`，按 `bigrams` 处理：
   - 先 `strings.ToLower`，只保留字母与数字。
   - 取相邻两个字符组成字符对，去重成集合。
   - 空格被去掉，所以正文末字与关键词首字也会组成字符对。索引必须复现这一点。
3. `overlap = |Q ∩ D| / |Q|`，`rel = max(向量分, overlap)`。
4. 查询非空且 `rel == 0` 的记录被排除；查询为空时，所有有效记录都参与打分。
5. 分数计算与排序（分数降序，ID 升序）不变。

## 3. 索引结构

```go
// bigram 是两个字符打包成的键：string(rune 对) 与 (r1<<32 | r2) 一一对应，不分配字符串。
type bigram uint64

type bigramIndex struct {
    version  int                  // indexVersion，见第 5 节
    ids      []string             // 文档序号 → 记录 ID，只含有效记录
    postings map[bigram][]int32   // 字符对 → 包含它的文档序号（每个文档在每个列表中至多出现一次）
}
```

- **构建**：对每条有效记录生成打包后的字符对，排序去重后追加到倒排表。
  - 规范化与 `bigrams` 完全一致：`unicode.ToLower` 逐字处理，等价于 `strings.ToLower`，用测试固定这一点。
  - 只保留 `IsLetter`/`IsDigit`。
  - 用同一个拼接后的文本。
  - 现有的 `bigrams` 改为同一套实现：查询端也用打包键，消除查询本身的分配。
- **查询**：
  1. 对查询求字符对集合 `Q`。
  2. 对 `Q` 中每个字符对，遍历它的倒排表并累加计数，计数器是长度为文档数的 `[]uint16`，取自池中。
  3. 计数大于 0 的文档，以及向量命中的文档，构成候选集。
  4. `overlap = 计数 / |Q|`，与现在的整数除法完全相同。
  5. 查询为空时候选集为全部有效记录，与现在相同。
  6. `Kinds` 过滤、打分与排序沿用原代码。
- **复杂度**：由"所有记录的全部字符对"降到"查询字符对的倒排表长度之和"。常见字符对（如"用户"）的倒排表可能很长，最坏情况是所有记录都包含它，但只是一次整数累加，没有分配。

## 4. 生命周期与增量提交的配合

索引是 state 的**派生数据**，只存在于内存中，不落盘。

| 层 | 内容 | 何时构建 | 缓存键 |
|---|---|---|---|
| 基础快照索引 | 基础快照中全部有效记录 | 解码基础快照时（"随 state 解码构建"） | (作用域, base.commit_id)，与已解码的基础快照放在同一个缓存条目 |
| 覆盖层索引 | 覆盖层中被改动、且仍有效的记录（至多数千项） | materialize 时 | (作用域, head.commit_id)，与已还原的 state 放在同一个条目 |
| 遮蔽集 | 覆盖层中出现过的记录 ID 在基础快照中的序号（位图） | materialize 时 | 同上 |

- **查询**：
  1. 先在基础快照的倒排表中查，跳过被遮蔽的序号，因为这些记录已被覆盖层修改、失效或删除。
  2. 再在覆盖层的倒排表中查。
  3. 候选集取两者的并集。
- 结果等于"对当前 state 重新构建完整索引"的结果：基础快照中未被修改的记录，它的文本与有效性都没变。
- **为什么依赖增量提交**：在 G1a 的整份重写模型下，每次提交都产生新的 state，下一次召回必须为整份 state 重建索引。这和现在每次重算字符对是同一个量级的开销，跨实例召回得不到改善。增量模型下：
  - 基础快照只在压缩时变化，它的索引在两次压缩之间一直复用。
  - 每次提交只需重建覆盖层索引，开销与覆盖层大小成正比。
- **失效**：
  - 基础快照的缓存条目被淘汰或压缩：它的索引随之失效。
  - head 变化：覆盖层索引与遮蔽集随还原出的 state 一起失效。
  - Purge：作用域改变，全部失效。
  - 索引不可变，构建后由多个读者共享，没有并发写。

## 5. 版本与一致性

- `indexVersion` 是代码常量。字符对的规范化或打包方式改变时递增，旧版本的索引在缓存中不被采用。索引不落盘，因此没有存储兼容问题。
- **召回结果的稳定性**：
  - 召回的结果只决定 `Snapshot` 的引用，引用写进持久日志，`Hydrate` 不重新打分。
  - 所以索引不影响 G0 的恢复与意图字节。
  - 但召回结果必须逐项不变，否则同一查询在升级前后会召回不同的内容。这一点用等价测试强制，见第 7 节。
- **缓存命中与完整解码等价**：
  - 索引是 (基础快照, 覆盖层) 的确定性函数，两者在缓存路径与完整解码路径上逐字节相同（G1a 的 `normalize`）。
  - 测试断言两条路径的索引查询结果相同。

## 6. 内存上限

- 估计（待测）：5k 条记录约 50 万个倒排项，`int32` 约 2 MiB；字符对键与切片头约 5～8 MiB。
- 基础快照索引的实际堆占用计入 `StateCacheBytes`：
  - 在估计堆占用时，加上按记录数计的索引估计值。
  - 该估计值按第 7 节的实测标定，不另设配置项。
- 小于 200 条记录的 state 不建索引，直接逐条计算：此时两者开销相当，节省的是内存。

## 7. 基准与验收（实施前不视为已证明）

| 项 | 方法 | 验收标准 |
|---|---|---|
| 等价性 | 对 1k、5k 两种规模、两组数据，比较索引路径与原实现的 `[]Scored`（ID、`Relevance`、`Score` 逐位相同，顺序相同）。查询共 2,000 个：记录正文的子串、实体名、随机汉字、中英文混合、空查询、带 `Kinds` 过滤。另对随机生成的覆盖层（修改、失效、删除、新增）重复一遍 | 100% 相同 |
| 构建耗时 | 基础快照索引；1k、3k、5k；两组数据；28 核与 4 核 | 5k、4 核时 p95 ≤ 15ms |
| 覆盖层索引 | 覆盖层 0～2,000 项 | 2,000 项时 ≤ 3ms |
| 召回计算 | `Snapshot` 加 `Hydrate`，state 预先读好（与 G1 7.7 的口径相同） | 5k、两组数据、两种核数，p95 ≤ 8ms |
| 完整召回 | 两次读取加计算，FileStore 与 pgstore，热与跨实例（在增量提交实施后测） | 5k 时 p95 ≤ 30ms |
| 内存 | 基础快照索引的存活堆（与 G1 7.3 的方法相同） | 5k 时 ≤ 16 MiB，并据此标定缓存估计 |

如果召回计算的 p95 达不到 8ms，先剖析剩余开销再决定下一步，不扩大索引范围。剩余开销可能来自 `Related` 的 5ms 和读取的拷贝。

## 8. 实施记录：与提案的差异（2026-11-11）

代码：`memory/recall_index.go`；等价测试：`memory/recall_index_test.go`。

| 项 | 提案 | 实施 | 原因 |
|---|---|---|---|
| 倒排表结构 | `map[bigram][]int32` | 排序数组：每项把（首字 21 位、次字 21 位、记录序号 22 位）打包成一个 `uint64`。构建是并行的"逐条提取 + 分段排序 + 两两归并"，查询是二分查找 | 映射加小切片的构建在低压缩率数据上要 45ms（几乎每个字符对都不同，产生几十万个小切片）。排序数组降到 6～13ms，也不再产生大量小对象 |
| 构建时机 | 解码时同步构建 | 解码时在**后台**开始构建（`lazyIndex`），读取不等待；召回时若尚未完成则等待（`sync.Once`）。遮蔽集与覆盖层的字符对也推迟到第一次查询时计算 | 同步构建使 4 核、低压缩率数据的冷读 p95 达到 35ms，超出 30ms 阈值。冷召回（读取、解码、等待构建）单独作为指标报告 |
| 召回入口 | — | `recallState`：读取、查候选、打分、排序，返回排好序的结果，即 G1a 门槛的"端到端召回"。不含向量召回（需要嵌入模型）；G1b 把公开的 `Recall` 接到这里 | 用户 2026-11-11 确定以端到端召回 p95 ≤ 30ms 作为门槛，设计目标 ≤ 20ms |
| 内存估计 | 按实测标定 | 每条记录 1,200 字节，计入缓存容量 | 排序数组每个字符对 8 字节，每条记录约 100～150 个字符对 |

**等价性**：

- 规模与查询：150 条（不建索引的路径）与 1,000 条，两组数据，各 1,000 个查询。
- 两个阶段：只有基础快照；以及基础快照加覆盖层（修改正文、失效、恢复、删除、新增）。
- 比较项：与原 `recall` 的 `[]Scored` 比较 ID、`Relevance`、`Score`（浮点数逐位相同）与顺序。
- 结果：全部 8,000 个查询相同。
