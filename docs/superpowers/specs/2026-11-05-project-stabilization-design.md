# 项目稳定化设计

## 目标与授权

按项目现状分析中给出的四项建议顺序执行；用户已明确要求“按照顺序执行”。本次落实复现入口、公共契约、业务恢复验收和覆盖率门禁，不发布版本、不推送分支、不操作真实支付。

## 方案

复用现有 Makefile、Go 验证命令、契约测试和退款恢复案例，避免建立第二套工作流系统。开发工具链以主模块声明为准；独立性能评测仍保持独立模块。跨仓测试使用临时 modfile 将本地关联模块替换为当前源码，不修改下游 go.mod/go.sum/go.work。

曾考虑只整理文档，无法防止独立模块与关联仓库再次漂移；也考虑引入全局 go.work，会改变下游默认解析行为。因此采用现有入口加显式验证的方式。

## 交付

1. 主模块声明推荐 Go 1.26.10（最低 Go 1.26.0）；Makefile 和 CI 遵循该声明，处理陈旧 GOROOT。更新 frameworkbench 的依赖并加入只读依赖验证，修正文档。
2. 记录现有 Runnable、模型流、Store、审批与预算的公共行为及变更规则；提供本地关联仓库验证命令，缺少模块或测试失败时明确失败，报告保留实际跳过项。
3. 对已有退款恢复案例执行授权拒绝、重复提交、跨进程崩溃、订单变更、过期和版本拒绝验收。真实业务测试环境另需业务端点、认证方式与测试数据；没有这些输入时只声明本地合成验收结果。
4. 整体覆盖率由 45% 提至 75%，维持现有核心阈值，并增加 multiagent ≥85% 门禁；回归检查临界值、缺失模块和高整体覆盖率掩盖低模块覆盖率的情况。

## 边界

- 不改变现有公共函数签名和持久化格式，不增加兼容别名；破坏性变化继续采用新版本与迁移说明。
- 不接触用户原有未跟踪的沙箱研究资料；关联仓库仅用于本地验证。
- 使用当前工作目录的新分支承载改动，保留已有资料；不创建需要额外同意的 worktree。
- 真实数据库测试必须明确标识跳过，不把跳过当作通过；本地账本不是支付方回执。

## 验收

主模块全量 race/覆盖率、build、vet、v2 lint、导入检查通过；frameworkbench 在 -mod=readonly 下通过；本地关联模块使用当前源码执行测试并输出结构化报告；退款故障恢复测试有可追溯结果。没有真实业务环境时验收报告明确保留该项。
